# 开发计划 · 核心资产备份与维护

> 状态：**已确认（2026-10-18）** · 定位：独立运维工作流（与第四阶段服务运维互补）
> 背景：数据库不入 git（含密码哈希/密钥），丢失不可再生（用户账号、视图规则、手工别名、
> 东财已下架历史段）；本地按天备份只能防误删与代码写坏，防不了硬件损坏与慢性损坏

## 设计原则

1. **可验证的备份才算备份**：每份快照落盘即 `PRAGMA integrity_check` + 数据新鲜度抽查，sha256 记入 manifest
2. **一致性快照**：SQLite 用在线备份 API（`Connection.backup()`），不拷贝正在写入的库（calc 每晚 VACUUM）
3. **GFS 分层保留**：30 日 + 12 周（每周最后一次快照）+ 12 月 —— 慢性损坏 40 天后仍可回溯一年
4. **高危操作前置快照**：`sector.py calc` 全量重算前自动打 `pre-calc` 标签快照（防自己的代码写坏数据）
5. **恢复必须演练**：`verify` 子命令随时校验任意快照；恢复前自动打 `pre-restore` 快照兜底

## 实现（`core/backup.py`）

| 子命令 | 行为 |
|---|---|
| `now [-t tag]` | 立即快照全部资产；sha256 与该资产最近一次相同 → 跳过（节假日不占空间） |
| `daily` | `now` + `prune`（任务计划程序每日入口，收盘任务链后 18:30） |
| `prune` | GFS 清理：每资产保留 最近30份 ∪ 最近12个ISO周各1份(周内最新) ∪ 最近12个月各1份 |
| `list` | 备份清单（时间/资产/大小/标签/校验状态） |
| `verify [file\|--all]` | 文件存在 + sha256 比对 + integrity_check + 新鲜度查询 |
| `restore <file> --yes` | 先校验 → 打 pre-restore 快照 → 原子替换目标 |

- 备份目录 `backups/`（gitignore）；清单 `backups/manifest.json`
- 命名 `{asset}_{YYYYMMDD_HHMMSS}[_{tag}].db|.bin`
- 资产缺失 → 告警跳过不报错（各环境资产集不同）

## 调度与文档

- `scripts/backup_daily.bat`（CRLF）：`python core\backup.py daily >> backups\backup.log`
- `scripts/install_backup_task.bat`：`schtasks /Create ... /SC DAILY /ST 18:30`（独立于 Web 服务存活）

# 第二步 · B1 备份服务化（执行稿 · 2026-10-18 细化确认）

> 前置：第一步（core/backup.py CLI）已上线 · 改动：`core/backup.py`、`server/{models,jobs,routes_admin}.py`、`data.html`、迁移、测试

## B1-1 core/backup.py v2（类型化）

- **tag → type 字段**：`daily | weekly | manual | pre-calc | pre-restore`；文件名 `{asset}_{ts}_{type}.db`
- **保留策略按类型滚动**（替代 GFS；monthly 移除——需求即日/周两档）：
  `prune(retention={daily:14, weekly:8, manual:5, pre:10})`，每资产每类型留最近 N 份；
  **每资产最新一份永不删**（底线保护）
- **旧 manifest 兼容**：无 type 的历史条目按 tag 归一（空→daily，pre-\*→pre）
- **文件日志**：`backups/backup.log` 逐行追加（时间/动作/资产/结果），`_log()` print+文件双写
- **编程接口** `run_all(btype) -> {status, files[], total_mb, error}` 供服务 in-process 调用；
  stdout.reconfigure 移入 `__main__`（import 安全）

## B1-2 服务端（server/）

**设置存 AppSetting（DB 热更新，与 update_cron 同机制；不用 server.yaml）**：
```
backup_enabled=1  backup_daily_cron="18:35"  backup_weekly_cron="fri 18:45"
backup_daily_n=14 backup_weekly_n=8  backup_manual_n=5
```

- **models.BackupRun**：id/btype/trigger/status/files_n/total_mb/duration_s/error/files_json/started_at/finished_at + alembic 迁移（head=2c59761f16a1）
- **jobs.task_backup(btype, trigger)**：in-process 调 `backup.run_all` + 类型滚动 prune → 写 BackupRun；入单工作线程队列（与数据任务互斥）
- **调度**：`_sync_cron_jobs` 增 `daily_backup`（每日）与 `weekly_backup`（解析 `"fri 18:45"` → day_of_week+HH:MM），策略保存即热生效
- **API（require_level 7）**：
  | 方法 | 路径 | 行为 |
  |---|---|---|
  | POST | `/admin/api/backup/run` | `{type}` 入队，返回 job 排队信息 |
  | GET | `/admin/api/backups` | BackupRun 历史 + 摘要（各类型最近成功/份数/磁盘占用） |
  | POST | `/admin/api/backup/settings` | 保存策略（开关/时刻/保留数量校验）+ reschedule |
  | POST | `/admin/api/backup/verify` | 同步全量校验（sha+integrity，~3s），返回逐条结果 |
  | POST | `/admin/api/backup/restore` | 恢复；**守卫**：app 资产在线拒（提示停服 CLI 恢复）、队列忙拒 |

## B1-3 数据管理页「数据备份」卡（data.html）

- [立即备份]：类型下拉（手动/日备/周备）→ loading 反馈 → 历史自动刷新
- 策略区：日备开关+时刻、周备开关+周几时刻、三个保留数量 → 保存即热生效
- 历史表：时间/类型/触发/文件数/大小/耗时/状态（失败展开 error）＋逐行 [校验] [恢复(confirm)]
