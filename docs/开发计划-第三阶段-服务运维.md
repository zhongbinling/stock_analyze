# 第三阶段开发计划 · 服务运维管理（概要）

> 状态：**概要（第二阶段完成后细化执行稿）** · 日期：2026-10-15
> 目标：为本项目（及后续多视图类型）提供**三环境（开发/灰度/产线）的服务运维能力**：部署、更新、启停、状态展示，独立运维账号登录。

## 1. 环境模型（单机多实例起步，可平滑迁多机）

| 环境 | 目录约定 | 端口（默认） | 用途 |
|---|---|---|---|
| dev 开发环境 | `<repo>`（本机开发仓） | 8501 | 日常开发调试，数据可随时重建 |
| staging 灰度环境 | `deploy/staging/`（独立副本+独立venv/数据） | 8521 | 发布前验证：跑迁移、生成测试视图、走完整链路 |
| prod 产线环境 | `deploy/prod/`（独立副本+独立venv/数据） | 8530 | 对外服务，仅由发布流更新 |

- 三环境**共享同一 git 远程**；staging/prod 为仓库工作副本，各自 `data/`、`core/data/`、`views_store/` 完全隔离
- 环境清单落在运维库 `ops.db`（environments 表：名称/路径/端口/当前commit/角色），新增环境即加一行

## 2. 运维系统形态

- **独立的 Flask 应用** `ops/`（与业务 `server/` 分离，独立端口 8500），只绑定 127.0.0.1（远程运维建议 SSH 隧道或反代+IP白名单）
- **独立运维账号体系**（`ops_users` 表 + 独立登录/限速/审计 `ops_log`），与业务账号（users 9级）完全隔离——运维权限只属于运维系统，不与业务等级互通
- 复用第一阶段资产：svc.py（启停/健康）、deploy 流程（venv/依赖/迁移）、bootstrap

## 3. 功能清单

| 模块 | 内容 |
|---|---|
| 环境总览 | 每环境卡片：健康状态(/healthz)、版本(当前commit+`__version__`)、PID/端口、最近部署时间、数据新鲜度（行情最新日期） |
| 部署/更新 | 对指定环境执行：git pull → 依赖刷新 → `db upgrade` → 重启（即 deploy 流程的参数化调用）；支持指定 commit/分支（回滚前置） |
| 启停管理 | start/stop/restart/status（转调该环境副本的 svc.py），显示实时日志尾 |
| 日志查看 | 环境服务日志 `data/service.log` 在线 tail（最近N行自动刷新） |
| 发布流 | dev → staging → prod 的**逐级推广**按钮（记录推广单：源commit→目标环境/时间/操作者）；prod 支持一键回滚到上一 commit |
| 审计 | 全部运维操作（部署/启停/推广/回滚）落 ops_log，页面可查 |

## 4. 阶段拆分（概要）

| 阶段 | 内容 | 交付 |
|---|---|---|
| S9 三环境模型与部署单元 | deploy 脚本参数化（`--env staging/prod` + 目录/端口/数据隔离）；ops.db 与环境清单；staging 首次拉起 | 单机三实例并存、互不干扰，验收：三端口健康检查全绿、数据隔离验证 |
| S10 运维系统 | ops/ 独立应用：运维账号登录、环境总览、部署/更新、启停、日志、发布流与回滚、审计 | 验收：经运维页完成一次 dev→staging→prod 完整发布与一次回滚，全程不碰命令行 |

## 5. 与现有设施的关系

- `scripts/svc.py`、`deploy*.sh/bat` 保持通用工具属性；运维系统是它们的**编排与可视化层**（subprocess 调用，不重复实现）
- 业务服务（server/）零改动；运维系统故障不影响已部署环境运行
- 未来多机迁移：环境表加 host 字段，svc 调用改 SSH 即可（本阶段不做）
